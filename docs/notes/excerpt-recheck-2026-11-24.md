For each row, subagents used WebFetch to fetch the first source and asked whether the excerpt occurs on the page. When that failed they tried the next source, and then one web search for an exact phrase, accepting only the same publisher or an exact syndicated copy. No curl, archives or mirrors were used.

**Limits of this run.** No one was there to approve WebFetch's permission prompts, so WebFetch refused most URLs taken straight from the rows. Only URLs that a web search had returned could be fetched. Partway through, the run also used up its shared web-search budget (200), and the last batches got no search fallback at all. So nearly every row marked *unreachable* below failed because of this run's own limits, not because the site was down. These rows need another pass in a session where WebFetch is allowed (for example a live session, or a scheduled task set to approve automatically).

**What was written to Airtable.** A `[Excerpt re-check 2026-11-24]` line was added to the Machine note of the 111 rows that were confirmed or closely matched. No Flags, Decisions or other fields were changed. The 103 unreachable rows were deliberately left without a re-check line. The task skips any row whose note already has that marker, so writing "Still unreachable" there would stop the next run from checking them again.
