# 14: Extraction without an API key

**What to build:** The weekly run proposes candidates without a paid API key: the extraction step runs on the maintainer's Claude subscription through the Claude Code GitHub Action (secret `CLAUDE_CODE_OAUTH_TOKEN`), and the same prompt files can be answered in a live session when no credential is set. A relevance filter and a per-run cap keep the subscription cost small.

**Blocked by:** 07

**Status:** built (2026-10-26). Same day, the maintainer decided on no external key or token at all: the weekly run is a scheduled task on his Claude subscription performing the session route (decision 08, second amendment); the workflow's cron was removed and the GitHub Action route stays available on demand should a token ever be added. First live harvest from a session: see below.

**Why.** Ticket 05's live run has waited since 2026-10-15 for `ANTHROPIC_API_KEY`; the maintainer cannot fund API billing. GitHub Models, considered as a free route, was retired on 2026-07-30. The Claude Code GitHub Action accepts a subscription token (`claude setup-token`; Pro, Max, Team and Enterprise plans) and its runs "use your Claude subscription instead of API billing" (code.claude.com/docs/en/github-actions). The extraction prompt, the parsing and every check stay the pipeline's (ADR 0003 unchanged); only who answers the prompt changes, and the answerer is named in the `extractor` field so the agreement report keeps the routes apart.

- [x] `harvest prompts` writes a run's extraction prompts as files (the system prompt once, one user prompt per document, an index) and `harvest extract --recordings` consumes the answers in the recorded-response format, so prompts answered by any route yield the same candidates as a direct extraction. Seam-2 test: the fixture captures, written as prompts and answered from the fixture recordings, extract to the same `candidates.csv` as the recorded extractor. *`extract.write_prompts` / `prompt_key` (the recording key, so an answer file is a recording); `harvest prompts --captures --out [--max-documents N] [--all] [--answered-by claude-code/<model>]` (the exact `model` string every answer carries, so the extractor id names the route rather than whatever each subagent calls itself); `harvest extract --prompts DIR` restricts the run to the index's selection and refuses prompts written for another system prompt. `RecordedClient` tolerates what a hand-writing answerer gets wrong: an answer file that is not JSON, or has no `text`, fails that document only (retried next run), and `text` may be the answer object itself rather than an escaped string. An answer without token counts gives cost "unknown". `user_prompt` cuts a document at `MAX_DOCUMENT_CHARS` (20,000, the fetcher's own cut, so fetched captures are never cut twice and hand-made captures are bounded the same way on every route). `tests/test_prompts.py`: the seam-2 test answers with the route's model name and no counts and compares every column but `extractor`, which it checks separately.*
- [x] A relevance filter drops documents that name no South China Sea term or feature (gazetteer names and a multilingual term list), and `--max-documents` defers the rest, newest first; deferred documents are fetched again next run, irrelevant ones are not. Both are counted in `run.json`. *`pipeline/relevance.py`: `TERMS` (English, Vietnamese, Malay/Indonesian incl. press house styles such as `coastguard`, `Laut Tiongkok Selatan`, `Maritim Malaysia`; Chinese) plus every gazetteer name `usable_name` accepts, with the gazetteer's own folding and boundaries (so "Spratly-based" matches); `select` shares the cap round-robin across sources, newest first within each (publication date, then fetch time for listing pages, which carry none), so the undated agency listings are never crowded out by dated news feeds — the first design sorted by date alone and would have deferred every agency release for ever. In `extract_all` an irrelevant document is skipped and counted (`irrelevant`, also per source), a deferred one is a failure with `Extractor.DEFERRED` as its error (`deferred`), which `ops.drop_failed` already retries; deferred failures do not fail the run (`cmd_extract` exits 1 only on real failures without candidates), so a quiet week with a backlog still saves its state. A deferred document comes back only while its source still lists it (feeds list 15–40 items), so a standing backlog loses documents: the summary shows the deferrals, and `index.json` lists the dropped and deferred documents with title and url for spot-checking; the summary shows the first thirty dropped titles. The filter is loose on purpose: a wrongly kept document costs one prompt; a wrongly dropped one is lost, so the term list errs wide.*
- [x] The workflow runs without `ANTHROPIC_API_KEY`: with `CLAUDE_CODE_OAUTH_TOKEN` it answers the prompts through the Claude Code GitHub Action (a repository skill, `/harvest-extract`) and opens the review pull request as before; with neither secret it fetches and opens one "waiting for extraction" issue instead of a failure (closed by the next run that extracts). *`ROUTE` (dry | api | subscription | none) is computed once from the inputs and the secrets. The action step runs only when prompts were written, with `continue-on-error` (the extract step's exit code — no candidates and only real failures — judges the job), and with the skill's tools pinned in `claude_args` (`--allowedTools Read,Write,Glob,Agent --disallowedTools Bash`); a step after it fails the run if the working tree changed anywhere (the answers live in an ignored folder), so a prompt-injected document cannot reach the pipeline or the data through the agent. `github_token` is passed, so the Claude GitHub App need not be installed and `id-token` is not needed. A run on the `none` route does not push the state, so the documents are fetched again when a credential exists. The waiting issue is `ops failure-issue --kind waiting` (own label, title and marker; the next extracting run's `--resolved` closes both kinds). The dry run now goes through the prompt files too. The run's artifact keeps captures, prompts, answers and run report for 90 days. Not yet verified live: the action step (no token yet); whether subagents inherit the skill's tool grant is the one thing only that run can show (the skill falls back to answering in the main agent if they cannot write). Changed from the ticket text: captures are not saved to the state branch by a waiting run — they are kept 90 days as the artifact and re-fetched while the source lists them, which is cheap and keeps the state branch small; a document that falls off its source's listing before any run extracts it is lost.*
- [x] The session route is documented: a maintainer (or an assistant in a session) pulls the harvest state, writes the prompts, invokes `/harvest-extract`, extracts and opens the pull request with the existing commands. *README "Extraction without an API key", the waiting issue's body, and `.claude/skills/harvest-extract/SKILL.md` (the same skill the action runs; batches of eight through subagents; a missing answer is a wasted document, never a corrupted one; the agent never runs the pipeline or commits).*

**For the maintainer.** (1) Install Claude Code on your computer: `npm install -g @anthropic-ai/claude-code` (needs Node.js 18 or newer) or the installer linked at claude.com/claude-code. (2) Run `claude` once and sign in with your Claude account. (3) Run `claude setup-token`; copy the token it prints (long-lived, not permanent: when a run fails with an authentication error, repeat this step and replace the secret). (4) GitHub → the repository → Settings → Secrets and variables → Actions → New repository secret → name `CLAUDE_CODE_OAUTH_TOKEN`, paste, Add. (5) Actions → harvest → Run workflow (dry run off) with an account that has write access; a success is a `harvest/<run_id>` pull request with a review page, a failure is an issue labelled `harvest-failure` with a link to the log. From then on the run repeats every Monday 06:17 UTC and spends from your subscription's usage at that hour; removing the secret or disabling the workflow pauses it. Scale: a run answers up to `max_documents` (80) prompts, each the ~5,000-character system prompt plus a document of up to 20,000 characters, in batches of eight through subagents — of the order of a million tokens a week at the cap, far less in a quiet week; the summary shows how many documents were deferred, and if that is above zero two weeks running, raise `max_documents` or accept that the oldest are lost. One check only a live run can make: the action refuses scheduled runs attributed to a bot account (the user who last changed the workflow's `cron` line); it is a person here, so this should pass.*
