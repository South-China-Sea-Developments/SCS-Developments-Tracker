# 13: Airtable review front end

**What to build:** A coder who prefers Airtable reviews the same candidates there and their decisions land in the pull request exactly as if made on the review page.

**Blocked by:** 06

**Status:** done (2026-10-19). Live base `SCS Developments Tracker — review queue` (`appK9OckCTV15vQwx`) in the maintainer's Airtable workspace "South China Sea Tracker", table `Candidates`, interface "Review queue" (a record-review page with Undecided/Decided tabs, grouped by claimant); PR #17's 24 candidates are in it. The repository's REST client (`AIRTABLE_TOKEN`) has run only against the fake and the recorded shapes; the live loading was done through the maintainer's Airtable connector, which is why `pull --from` accepts that client's export shape too.

- [x] Candidates of an open PR are mirrored into an Airtable base with the same fields and decision options. *`python -m pipeline.airtable push --run <run_id> --pr N` creates one record per candidate with the review page's context (dates, place, summary, actors, sources and excerpts, the suggestion and its reasoning, the machine note, the possible duplicate, the claimant's previous-year and same-year moves) and the coder's columns: `decision` (undecided / merge / new_move / duplicate / reject), the merge target (an existing move or another candidate of the batch), `duplicate_of`, the new move's type, criterion, year, ongoing_through, dyads, domains, issues, sub-regions and description, the nine editable event fields as `edit_*`, `note`, `reviewer`. Idempotent by `event_id`: a second push refreshes the context columns and never touches the coder's. `records --run` writes the same records as JSON without calling Airtable; `schema` prints the table as Airtable needs it (the live base was created from it).*
- [x] Decisions made in Airtable are written back to the PR as commits; Airtable is never read by the loader, validator or site build. *`pull --run <run_id> --out decisions.json` (or `--from export.json` for records exported by another client) emits the review page's own decisions file — same keys, same shapes, records still `undecided` skipped, blank `edit_*` columns meaning "keep" — which `python -m pipeline.queue decide decisions.json` applies on the run's branch as before; the commit is the same commit the page route makes. `tests/test_airtable.py` checks by AST and by a clean subprocess that `load_mats`, `validate`, `queue`, `harvest`, `release`, `agreement`, `gazetteer` and `web/*.py` never import `pipeline.airtable`.*
- [x] Seam-1 test: the same fixture PR reviewed via Airtable and via the review page yields identical files. *`test_same_decisions_through_airtable_and_through_the_review_page_yield_identical_files`: the fixture run is opened on two copies of the data; one is decided in a fake Airtable (same client interface, in memory) and pulled, the other given the page's export; after `apply_decisions` the five CSV files compare byte-identical.*
- [x] The sync can be disabled by configuration with no effect on the rest of the system. *`pipeline/airtable.json` `enabled: false`, a missing `base_id` or no `AIRTABLE_TOKEN` make every command print why and exit 0 without a request (tested with a client that fails the test if called). Nothing else reads the file.*

**Budget.** The free plan allows 1,000 API calls per workspace per month and 1,000 records per base. Records travel ten per call and every command counts its calls and stops before `--max-calls` (default 200); a 24-candidate push is three calls, a pull one or two. `clear --run` removes a decided run's records so the base stays small; the files in the repository are the record.

**Not done.** No automation inside Airtable (no webhooks, no scheduled pull): the sync runs when a person runs it, which is what ADR 0004 asks for (safe to switch off at any time). The REST client has not been exercised against the live base from this repository because no `AIRTABLE_TOKEN` secret exists; when the maintainer adds one, `python -m pipeline.airtable pull --run manual-20261018-new-claimants --out d.json --max-calls 5` is the first live test.
