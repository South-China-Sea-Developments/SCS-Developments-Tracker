# 13: Airtable review front end

**What to build:** A coder who prefers Airtable reviews the same candidates there and their decisions land in the pull request exactly as if made on the review page.

**Blocked by:** 06

*Extended by ticket 20 (the workbench: run log, sources, hand-off, sidelines, notes, flags and a dataset status); the current layout of the base is in `docs/airtable-workbench.md`.*

**Status:** done (2026-10-19; reviewed, fixes applied). Live base `SCS Developments Tracker — review queue` (`appK9OckCTV15vQwx`) in the maintainer's Airtable workspace "South China Sea Tracker", table `Candidates`, interface "Review queue"; PR #17's 24 candidates are in it. *Rebuilt 2026-11-07 at the maintainer's ask ("more interactive and easy to follow and track"): four pages — **Overview** (a dashboard: to decide / decided / new moves / merged / duplicates / rejected / flagged as possible duplicates / in all, bar charts by claimant, suggested type, sub-region, harvest run and decision, dropdown filters on decision, type and sub-region, and a grid of what is still to decide, oldest event first), **Queue** (a grid grouped by harvest run with tabs To decide / Possible duplicates / Decided / Needs a note — rejects without the required note), **Board** (a kanban by decision, cards coloured by suggested type, a count per column; dragging a card is a decision), **Review one by one** (the record-review flow, grouped by run and claimant, the fields in reading order: the event, the source, the machine's suggestion, the moves already in the dataset, then the decision). Queue, Board and the Overview grid open a candidate into the **Candidate Detail** page, whose groups separate what the source says, the machine's suggestion, the moves already in the dataset, the decision, the new-move fields and the optional corrections. All fields stay editable (the connector cannot set a field read-only on a detail page); the sync refreshes the context columns, so stray edits there are overwritten. Pages are published; ids: Overview `pagAWLTLoyKhRv2Sp`, Queue `pagzfbBYQDORsMZiT`, Board `pagsOwyf3mnYRnPSz`, Review one by one `pag2P7Or0IlDcHTI7`, Candidate Detail `pagZA6SQiPZBSV4uM`.* The repository's REST client (`AIRTABLE_TOKEN`) has run only against the fake and the recorded shapes; the live loading was done through the maintainer's Airtable connector, which is why `pull --from` accepts that client's export shape too. Decision 07's rule names the review page; after this ticket the maintainer's own review may equally be made in Airtable — either way `decide` makes the commit, and the rule's substance (nothing merged until he has reviewed it himself; no further candidate sets until he asks) is unchanged.

- [x] Candidates of an open PR are mirrored into an Airtable base with the same fields and decision options. *`python -m pipeline.airtable push --run <run_id> --pr N` creates one record per candidate with the review page's context (dates, place, summary, actors, sources and excerpts, the suggestion and its reasoning, the machine note, the possible duplicate, the claimant's previous-year and same-year moves) and the coder's columns: `decision` (undecided / merge / new_move / duplicate / reject), the merge target (an existing move or another candidate of the batch), `duplicate_of`, the new move's type, criterion, year, ongoing_through, dyads, domains, issues, sub-regions and description, the nine editable event fields as `edit_*`, `note`, `reviewer`. The coder's columns are prefilled as the page prefills them (the suggested type, dyads, domains, issues and the event's sub-region as the new move's; the machine's duplicate flag as `duplicate_of`; year and description blank, which `decide` defaults to the event's year and summary as the page does). Idempotent by `event_id`: a second push refreshes every context column (blanking one that became blank) and never touches the coder's. `records --run [--pr N]` writes the same records as JSON without calling Airtable; `schema` prints the table as Airtable needs it (the live base was created from it).*
- [x] Decisions made in Airtable are written back to the PR as commits; Airtable is never read by the loader, validator or site build. *`pull --run <run_id> --out decisions.json` (or `--from export.json` for records exported by another client, filtered to the run) emits the decision objects the review page exports, under the keys `decide` reads (the page's file also carries `run_id` and `exported`, which `decide` ignores): records still `undecided` skipped; a blank `edit_*` column, or one repeating the value shown, means "keep", as on the page; a decided row without an `event_id` is refused. `python -m pipeline.queue decide decisions.json` applies it on the run's branch as before. So that the commit is the same whichever front end exported the file, `apply_decisions` now applies a batch in events.csv order whatever the order in the file (new moves were numbered in file order before; the page exports in card order, which is events.csv order, so page results are unchanged). `tests/test_airtable.py` checks by AST (every `pipeline/*.py` but `airtable.py`, and `web/*.py`) and by a clean subprocess that nothing that builds the dataset or the site imports `pipeline.airtable`.*
- [x] Seam-1 test: the same fixture PR reviewed via Airtable and via the review page yields identical files. *`test_same_decisions_through_airtable_and_through_the_review_page_yield_identical_files`: the fixture run is opened on two copies of the data; one is decided in a fake Airtable (same client interface, in memory, ten records a call, paged reads, records returned in a different order) and pulled, the other given the same five decisions written by hand in the page's export shape (as `tests/test_queue.py` does; the page itself is verified only at seam 1, per the spec), including two CN 2026 new moves whose event-id order differs from card order; after `apply_decisions` the five CSV files compare byte-identical.*
- [x] The sync can be disabled by configuration with no effect on the rest of the system. *`pipeline/airtable.json` `enabled: false` (even with a token and base set), a missing `base_id` or no `AIRTABLE_TOKEN` make every command that would call Airtable print why and exit 0 without a request; `schema`, `records` and `pull --from` never call it (all tested with a client that fails the test if called). Nothing else reads the file.*

**Budget.** The free plan allows 1,000 API calls per workspace per month and 1,000 records per base. Records travel ten per call and every command counts its calls and stops before `--max-calls` (default 200), a push checking its whole cost before sending anything; a 24-candidate push is four calls (one list, three batches), a pull one. `clear --run` removes a decided run's records so the base stays small; the files in the repository are the record.

**Not done.** No automation inside Airtable (no webhooks, no scheduled pull): the sync runs when a person runs it, which is what ADR 0004 asks for (safe to switch off at any time). The REST client has not been exercised against the live base from this repository because no `AIRTABLE_TOKEN` secret exists; when the maintainer adds one, `python -m pipeline.airtable pull --run manual-20261018-new-claimants --out d.json --max-calls 5` is the first live test.
