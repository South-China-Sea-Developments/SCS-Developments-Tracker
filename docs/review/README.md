# Review pages

One self-contained HTML page per harvest run, generated by `python -m pipeline.queue open` on the run's branch (`harvest/<run_id>`) and committed with the candidates. Open it from the checked-out branch in a browser: it lists every candidate with its source excerpt and link, the extractor's suggested coding and reasoning, duplicate flags, and the claimant's moves from the previous year and the current year. Decide each candidate (merge into an existing move or into one formed from another candidate in the same batch, form a new move with its intensification criterion, mark it a duplicate of an accepted event, or reject with a note), export the decisions file, and apply it on the run's branch:

```
python -m pipeline.queue decide decisions-<run_id>.json --reviewer "Your name"
git push
```

The page writes nothing itself; `decide` applies the whole file or nothing, running the validator first, and only a merged pull request changes the dataset. Drafts are kept in the browser's local storage until cleared with the button. Pages here are kept with the run they belong to; they can be regenerated with `python -m pipeline.queue page --run-id <run_id>`.

**Airtable instead of the page.** The same candidates can be mirrored into the project's Airtable base (`python -m pipeline.airtable push --run <run_id> --pr N`) and decided there in the "Review queue" interface: set `decision` and fill the columns it needs (`merge_into_move` or `merge_into_candidate`; `duplicate_of`; the `new_*` columns; any `edit_*` column to change the event; `note`, required for a rejection). Then `python -m pipeline.airtable pull --run <run_id> --out decisions-<run_id>.json` writes the same decisions file the page exports, and `decide` applies it exactly as above. Rows still `undecided` are left alone; `clear --run` removes a run's rows once its pull request is merged. The base is a front end only: nothing that builds the dataset or the site reads it (ADR 0004).
